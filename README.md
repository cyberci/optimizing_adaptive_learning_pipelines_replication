# Latency optimization and oracle-based failure diagnosis

Replication package for the article

> B. Forstner.
> *Latency optimization and oracle-based failure diagnosis in interactive
> adaptive learning pipelines.*
> Manuscript submitted for publication, 2026.

This repository contains the instrumented reference implementation of the
recommendation critical path studied in the article, the complete measurement
harness, the trained model artefacts, every result file the article quotes and
the scripts that draw every figure in it. Running `./run_all.sh` regenerates all
of it from scratch.

## What the article claims, and what reproduces it

| Claim | Reproduced by |
|---|---|
| The architecture supports **93.7 %** flow-band retention; the pipeline as implemented delivers **20.0 %**. The entire shortfall is in the predictor. | `experiments/bench_oracle.py`, `experiments/bench_tiers.py` |
| Two one-line configuration choices mask each other. Fixing the training label alone reaches **35.8 %**; raising the ensemble weight alone is *worse* than doing nothing (**12.4 %**); doing both reaches **88.6 %**. | `experiments/bench_tiers_alpha.py` |
| What remains after the label fix is bias, not noise: a single shared logit intercept moves the ensemble from **21.2 %** to **83.2 %** without retraining. The optimiser's curse does not explain the gap. | `experiments/bench_residual2.py`, `experiments/bench_residual.py` |
| Median recommendation latency falls from **3714 ms** to **10.6 ms** across five runtime variants, and the cost is dominated by a fixed per-invocation charge rather than by arithmetic. | `experiments/bench_latency.py` |
| Enumeration beats twenty-trial search up to a grid of roughly 2 × 10⁵ candidates, and Eq. (1) predicts that crossover from two fitted constants. | `experiments/bench_planner.py`, `experiments/bench_ensemble_cost.py` |
| The crossover moves by an order of magnitude across serving runtimes, so it must be calibrated rather than hard-coded. | `experiments/bench_runtimes.py` |
| The result survives stronger opponents — multivariate TPE, CMA-ES, random search at four budgets — and beyond the crossover a two-stage rule beats every search we measured. | `experiments/bench_baselines.py`, `experiments/bench_baselines_warm.py` |
| The bounded asynchronous hand-off lifts supported concurrency on 2 vCPU from **16** to about **100** simultaneous learners, roughly 100× the throughput. | `experiments/bench_concurrency_inproc.py`, and optionally the HTTP cross-check |
| Degradation of the four-tier fallback chain is invisible in availability terms but measurable in the domain metric: retention is flat from full availability down to 50 %. | `experiments/bench_degradation.py` |

`docs/MAPPING.md` maps every individual table and figure to the script and the
result file that produce it.

## An important caveat about the data

**No human-subject data are used anywhere in this package, and none is
required to run it.**

Coglica is an experimental research platform for game-based cognitive
assessment. Every domain-metric number in the article — every flow-band
retention figure — is a *simulation*: a population of synthetic learners is
drawn from a reconstructed response model (`src/cognitive_sim.py`), and the
recommendation pipeline is run against it in a longitudinal loop. The response
model reconstructs the platform's own scoring logic; it is not a fit to observed
learner behaviour, and the article does not claim that the retention percentages
predict what human learners would experience. What the simulation supports is
the *comparison* between components, because every arm of every comparison faces
the identical simulated population, and only the component under study differs.

The timing and concurrency measurements are not simulated. They are wall-clock
measurements of real model invocations on the machine described in
`docs/ENVIRONMENT.md`.

The two trained ensembles shipped in `data/models/` were trained on data
generated by that same simulator, using the platform's own training procedure —
same layer sizes, optimiser, loss, callbacks, batch size, epoch count and split
seeds.

## Layout

```
.
├── src/                    the reference implementation
│   ├── repro_paths.py      where everything lives; imported by every script
│   ├── cognitive_sim.py    the reconstructed response model and learner population
│   ├── engine.py           the five runtime variants V0-V4 of the planner
│   └── service.py          FastAPI reproduction of the suggest-param endpoint
├── experiments/            one script per measurement, each writing one JSON
├── figures/                the plotting scripts
│   └── output/             the rendered figures, PDF and PNG
├── results/                the measurement output quoted in the article
├── data/
│   ├── descriptors.json    the five task descriptors (Table 1)
│   └── models/             the three trained model artefacts
├── docs/
│   ├── MAPPING.md          which script produces which table and figure
│   └── ENVIRONMENT.md      the measurement environment and what depends on it
├── tools/check.py          pre-flight check: parses everything, reports what is missing
├── work/                   intermediate artefacts; gitignored, safe to delete
├── run_all.sh              reproduce everything
└── Makefile                the same, as targets
```

Every script resolves its paths through `src/repro_paths.py`, so the package can
be checked out anywhere and run from anywhere, and nothing is ever written
outside the package root.

## Quick start

```bash
git clone https://github.com/cyberci/optimizing_adaptive_learning_pipelines
cd optimizing_adaptive_learning_pipelines

python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

python3 tools/check.py        # parses every script, reports missing dependencies
./run_all.sh figures          # 10 s:     redraws every figure from the shipped results
./run_all.sh bench            # 40 min:   re-measures, reusing the shipped models
./run_all.sh all              # 45 min:   retrains, then measures, then draws
```

`make` exposes the same targets (`make figures`, `make bench`, `make all`) plus
`make venv`, `make check`, `make clean` and `make distclean`.

To run one measurement on its own:

```bash
python3 experiments/bench_tiers_alpha.py
```

Each script prints a table to stdout as it goes and writes its JSON into
`results/`. `run_all.sh` additionally captures each script's output into
`logs/`.

### The optional HTTP cross-check

The concurrency measurement is made in-process, because a FastAPI endpoint
declared with `def` is dispatched to an anyio worker thread pool, so a
thread pool over the same engine call reproduces the server-side queueing
behaviour without the HTTP framing. That substitution is validated against a
real HTTP measurement:

```bash
./run_all.sh loadtest
```

This starts `src/service.py` on `127.0.0.1:8111`, drives it with
`experiments/loadtest.py` and writes `results/results_load_V4.json`. It needs
FastAPI, Uvicorn and httpx, which are listed separately at the bottom of
`requirements.txt`.

## Expected runtime

On the 2 vCPU machine described in `docs/ENVIRONMENT.md`:

| Stage | Scripts | Wall clock |
|---|---|---|
| `figures` | 4 plotting scripts | 10 seconds |
| `train` | `train_models.py`, `train_variants.py` | 5 minutes |
| `bench` | the 13 measurement scripts | 40 minutes |
| `all` | everything above | 45 minutes |
| `loadtest` | the optional HTTP cross-check | 2 minutes |

These are measured, not estimated: they are the times `run_all.sh` reported on a
clean checkout of this package on the machine in `docs/ENVIRONMENT.md`. The three
longest single scripts are `bench_tiers_alpha.py` (13 min, twelve longitudinal
conditions), `bench_concurrency_inproc.py` (7 min) and `bench_degradation.py`
(5 min). Nothing needs more than about 1 GB of memory; `bench_baselines_warm.py`
peaks at roughly 250 MB when it enumerates the largest catalogued descriptor.

The timing results are sensitive to machine load. Run on an idle host, and read
`docs/ENVIRONMENT.md` before comparing any absolute latency number with the
article's.

## Reproducing the article's exact numbers

We ran the whole package from a clean checkout before releasing it. What we
found is worth stating precisely, because "reproduces exactly" is true of some
of it and not of the rest.

**Bit-identical for the figures.** `./run_all.sh figures` regenerates all sixteen
figure files byte for byte, PDFs included; the script pins `SOURCE_DATE_EPOCH` so
that Matplotlib does not stamp a run date into them.

**Exact, to the last digit, when the shipped models are reused.** Everything
that does not involve retraining a network is fully deterministic:
`bench_oracle.py` reproduces 93.7 % and the grid-refinement control digit for
digit, as do the oracle, rule-based and static-default arms of `bench_tiers.py`.
This is what `./run_all.sh bench` does, and it is the mode we recommend for
checking the article's numbers.

**Within a confidence interval after a retrain.** `./run_all.sh all` retrains
both ensembles first, and TensorFlow training is not bit-reproducible even at a
fixed seed — thread scheduling and oneDNN kernel selection differ between runs.
The retrained networks are slightly different networks, so every number that
depends on them moves a little. In our clean run every headline figure landed
within about two points, well inside the confidence intervals the article
reports: 20.0 % → 19.5 %, 35.8 % → 34.7 %, 88.6 % → 88.0 %, 12.4 % → 14.6 %.
The pattern — neither correction sufficient alone, one of them harmful alone —
is identical.

**Not at all, for the timings, and deliberately so.** Latency, throughput and
the fitted cost constants are properties of a machine, and the article's
argument is precisely that they must be calibrated per deployment rather than
assumed. `docs/ENVIRONMENT.md` explains which of those claims are nonetheless
machine-independent, and how to check the crossover claim on your own hardware
even though the constants behind it differ.

If a domain-metric number does not reproduce within its confidence interval,
that is a bug and we would like to hear about it.
